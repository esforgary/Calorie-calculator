# Kall — личный дневник питания

Адаптивное приложение на React + TypeScript + Vite. Статический интерфейс размещается на GitHub Pages, вход по личному логину и паролю и персональный дневник — в Supabase. Дневник доступен только после входа; без настроенного Supabase показывается экран авторизации с сообщением о конфигурации.

## Запуск

Нужен Node.js 24 и npm. В каталоге проекта выполните:

```powershell
npm ci
# .env.local уже настроен на этом компьютере; для нового подключения используйте .env.example
npm run dev
```

Заполните `.env.local` перед запуском. После изменения окружения перезапустите Vite. Команды проверки: `npm test`, `npm run build`; просмотр сборки: `npm run preview`.

## Подключение существующего Supabase

Отдельный проект для дневника не обязателен: можно добавить таблицу в существующую базу. Объекты дневника имеют префикс `kall_`; текущие таблицы других приложений SQL-скрипт не меняет. Auth и лимиты проекта при этом общие для всех приложений этого проекта.

1. Откройте нужный проект Supabase → SQL Editor. Выполните содержимое `supabase/schema.sql`. Скрипт создаст `public.kall_diaries`, политики доступа только владельцу и серверный счётчик версий. Его можно выполнять повторно.
2. В настройках API проекта скопируйте Project URL и **publishable key** (`sb_publishable_…`) либо старый публичный `anon` key.
3. Запишите их в `.env.local`:

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-public-publishable-or-anon-key
```

Название `VITE_SUPABASE_ANON_KEY` сохранено для совместимости; значение может быть новым publishable key. Переменные `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` предназначены для Next.js и здесь не читаются. Vite использует префикс `VITE_`.

Эти значения видны в браузерной сборке. Доступ к данным защищают Supabase Auth и RLS, а не скрытость публичного ключа. **Нельзя использовать `service_role`, `sb_secret_…`, пароль базы или токен управления Supabase**. Если секретный ключ когда-либо попал в клиентский код или Git, отзовите его в Supabase и замените.

В текущем проекте таблица `public.kall_diaries`, RLS и счётчик версий уже созданы. Инструкции выше нужны при подключении другого проекта. Если в нём таблица ещё не настроена, выполните SQL-скрипт и нажмите повтор синхронизации.

## Личный вход без регистрации

В приложении есть только вход с логином `esforgary`; формы регистрации и вызова публичного signup нет. Логин сопоставляется со служебным идентификатором Supabase Auth `esforgary@kall.invalid`. Он не является почтовым ящиком, письма на него не отправляются. Пароль проверяется Supabase и никогда не хранится в исходниках, клиентском коде или Git.

В текущем проекте личный пользователь настроен и подтверждён через Admin API; его прежний UUID сохранён. Для развёртывания приложения в новом проекте администратор один раз настраивает пользователя в Supabase Auth через Dashboard или серверный Admin API:

1. Включить провайдер Email (он используется для проверки пароля служебного пользователя).
2. Если личный пользователь уже создан и в его дневнике есть данные, изменить идентификатор этого же пользователя на `esforgary@kall.invalid`, задать выбранный владельцем пароль и отметить email подтверждённым. Сохранить прежний UUID — дневник привязан к нему. Если личного пользователя ещё нет, создать его с этим служебным email и `email_confirm: true` через Admin API или Auto Confirm User в Dashboard.
3. Отключить публичную регистрацию **Allow new users to sign up** для этого личного проекта. Не менять общие настройки другого приложения без проверки назначения проекта.
4. Выполнить `supabase/schema.sql`, если таблицы дневника ещё нет.

Публичный publishable key не может создать или подтвердить пользователя административным способом. Для настройки нового проекта потребуется административный доступ; пароль и service_role не нужно добавлять в GitHub Pages. Код формы входа сам по себе не создаёт пользователя. Состояние общего переключателя **Allow new users to sign up** в текущем проекте не проверено: отсутствие регистрации в интерфейсе не отключает публичный signup API.

Другие email не допускаются интерфейсом приложения. Серверная RLS отдельно ограничивает каждую запись UUID её владельца. Уже существующие чужие данные и аккаунты не удаляются. [Admin API: создание пользователя](https://supabase.com/docs/reference/javascript/auth-admin-createuser), [настройки Auth](https://supabase.com/docs/guides/auth/general-configuration).

Вход запоминается в этом браузере на **30 дней с момента авторизации**. Срок связан с ID пользователя и ID сессии Supabase, восстанавливается при перезагрузке и не продлевается при обновлении access token. Для расчёта используется время исходной аутентификации из JWT `amr`, а не меняющийся `iat`. Приложение проверяет срок при запуске, событиях авторизации, возвращении во вкладку, чтении и записи дневника; таймер закрывает уже открытый интерфейс по истечении срока. Выход сразу скрывает дневник и отзывает локальный допуск, даже если сеть недоступна. Очистка данных браузера или отзыв сессии могут потребовать войти раньше.

Это ограничение доступа в интерфейсе приложения. Настройка общего срока сессий на сервере Supabase (**Time-box user sessions**) доступна на Pro и выше; на Free защита облачных данных обеспечивается проверкой JWT и RLS. Изменения localStorage не должны рассматриваться как серверная проверка срока. [Сессии Supabase](https://supabase.com/docs/guides/auth/sessions), [JWT и время аутентификации](https://supabase.com/docs/guides/auth/jwt-fields).

## GitHub Pages

1. Загрузите проект в свой GitHub-репозиторий вместе с `package-lock.json`. `.env.local` не коммитьте.
2. Публичные URL и publishable key выбранного Supabase уже записаны в `.env.production`. Workflow использует их при сборке. Это клиентская конфигурация, а не административный секрет; приватность дневника обеспечивает SQL с RLS. Для другого проекта замените эти два значения.
3. В Settings → Pages выберите Source: **GitHub Actions**.
4. Отправьте изменения в `main` или `master` либо вручную запустите workflow **Deploy Kall to GitHub Pages**. Он выполняет установку по lockfile, тесты, сборку и загрузку `dist` в Pages.
5. После изменения `.env.production` заново запустите сборку: переменные встраиваются при компиляции. Вход по логину и паролю не использует перенаправления и не требует настройки Redirect URLs.

В Vite задан `base: './'`, поэтому ресурсы работают и в подпапке репозитория. Приложение не требует отдельного сервера Node.js для работы. [Документация GitHub Pages с Actions](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Данные и синхронизация

- Гостевой режим отключён. Старые гостевые записи сохраняются в хранилище браузера, но не показываются и **не переносятся автоматически** в аккаунт. У каждого аккаунта отдельный локальный кэш по ID пользователя; выход возвращает экран авторизации.
- Облачные данные сначала загружаются. Автосохранение начинается только после успешной загрузки; пустой экран при входе не заменяет облачный дневник. Во время загрузки изменения заблокированы. После сетевого сбоя можно работать с ранее сохранённым персональным кэшем; первый вход без кэша требует соединения.
- Изменения сохраняются локально сразу и отправляются в облако с небольшой задержкой. Без сети они остаются в браузере; повторите синхронизацию после восстановления связи. Не очищайте данные браузера, пока изменения не попали в облако или экспорт.
- Сервер увеличивает `revision` при каждом сохранении. Запись выполняется только при совпадении ожидаемой версии. При одновременном редактировании на разных устройствах конфликт останавливает отправку: новая облачная версия не затирается.
- При конфликте сначала экспортируйте текущий дневник, затем выберите загрузку облачной версии. Перед заменой приложение дополнительно сохраняет одну резервную копию в localStorage под ключом `kall:diary:USER_ID:v1:conflict-backup`. Если место закончилось, замена отменяется. Автоматического объединения двух версий нет.
- Повреждённый локальный JSON сохраняется без изменений в ключе с суффиксом `:corrupt-backup:TIMESTAMP` перед заменой. Если браузер не может записать резервную копию, исходный ключ не перезаписывается.
- На общем компьютере локальные копии остаются в браузере после выхода. Используйте отдельный профиль браузера и удаляйте его данные только после успешной синхронизации. Это важно для личной информации о здоровье.

Для восстановления из ранее скачанного JSON войдите в аккаунт и выберите «Восстановить из JSON» в «Профиль и цели». Импорт заменяет текущий дневник после явного подтверждения и скачивания его резервной копии. Экспортируйте дневник регулярно. Локальное хранилище может быть очищено браузером; облачная синхронизация не является историей резервных копий.

RLS проверяют через SQL/API в контекстах `anon`, владельца и другого авторизованного UUID: читать и изменять строку дневника должен только владелец. Интерфейс приложения не предназначен для входа тестовых пользователей. Проверку облака следует делать на реально настроенном проекте — локальная сборка сама её не подтверждает.

11 октября 2026 проверены вход на опубликованном сайте, восстановление сессии после перезагрузки, чтение и сохранение дневника, отказ анонимному доступу и чужому UUID, защита от записи устаревшей версии. Временная функция настройки входа закрыта и возвращает `410`. Supabase Security Advisor не обнаружил замечаний к таблице и RLS; отдельное предупреждение проекта — отключена [проверка паролей по базам утечек](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

## Изображения и ограничения

Без фотографии продукты и блюда отображаются SVG-значками выбранной категории: сыр, колбаса и сосиски, птица, сладкое, мучное и другие. Крупы, хлопья и макароны обозначены коробками разных цветов. Для рецептов доступны первое, второе, сэндвич, десерт, пицца, бургер и ролл; начинка сэндвича определяется по продуктам в составе. Старые записи получают подходящий значок по названию и категории.

Фото продукта уменьшается интерфейсом до 512 пикселей по длинной стороне, с ограничением результата 350 КБ. Изображение хранится в JSON как data URL. Это удобно для небольшого личного каталога; base64 увеличивает размер примерно на треть, а браузерное хранилище ограничено. Весь облачный дневник ограничен SQL-проверкой до 4 000 000 байт. Для большого каталога фотографий потребуется отдельный приватный Supabase Storage и ссылки вместо data URL.

Синхронизация передаёт весь дневник одной записью, история его версий не хранится. Рецепты и продукты вводятся вручную; шаги, прогулки и сон записываются пользователем, автоматического подключения к часам и шагомеру нет. Советы по времени активности показываются внутри приложения, фоновые push-напоминания не настроены.

## Расчёты

Калории продуктов, состав БЖУ, ИМТ, суточный ориентир, расход прогулок и сна являются оценками. Проверяйте значения продуктов на упаковке и указывайте вес съеденной порции. Калории сна и прогулок не следует повторно прибавлять к дневному бюджету, уже учитывающему обычную активность. Отдельный продукт сам по себе не гарантирует ускорения или замедления похудения: важны питание в целом, порции, сон, активность и особенности здоровья.

Расчёты предназначены для взрослого личного дневника и не заменяют медицинское назначение. При беременности, кормлении, возрасте вне диапазона 20–78 лет, заболеваниях или расстройствах пищевого поведения цели питания и нагрузки подбирают индивидуально со специалистом.
