# Kall — личный дневник питания

Адаптивное приложение на React + TypeScript + Vite. Статический интерфейс можно разместить на GitHub Pages, вход по email и паролю и персональный дневник — в Supabase. Без переменных Supabase приложение работает локально в текущем браузере.

## Запуск

Нужен Node.js 24 и npm. В каталоге проекта выполните:

```powershell
npm ci
# .env.local уже настроен на этом компьютере; для нового подключения используйте .env.example
npm run dev
```

Заполните `.env.local` перед запуском, если нужна синхронизация. Для локального режима удалите значения обеих переменных. После изменения окружения перезапустите Vite. Команды проверки: `npm test`, `npm run build`; просмотр сборки: `npm run preview`.

## Подключение существующего Supabase

Отдельный проект для дневника не обязателен: можно добавить таблицу в существующую базу. Объекты дневника имеют префикс `kall_`; текущие таблицы других приложений SQL-скрипт не меняет. Auth и лимиты проекта при этом общие для всех приложений этого проекта.

1. Откройте нужный проект Supabase → SQL Editor. Выполните содержимое `supabase/schema.sql`. Скрипт создаст `public.kall_diaries`, политики доступа только владельцу и серверный счётчик версий. Его можно выполнять повторно.
2. В настройках API проекта скопируйте Project URL и **publishable key** (`sb_publishable_…`) либо старый публичный `anon` key.
3. Запишите их в `.env.local`:

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-public-publishable-or-anon-key
```

Название `VITE_SUPABASE_ANON_KEY` сохранено для совместимости; значение может быть новым publishable key. Переменные `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` предназначены для Next.js и здесь не читаются. Vite использует префикс `VITE_`.

Эти значения видны в браузерной сборке. Доступ к данным защищают Supabase Auth и RLS, а не скрытость публичного ключа. **Нельзя использовать `service_role`, `sb_secret_…`, пароль базы или токен управления Supabase**. Если секретный ключ когда-либо попал в клиентский код или Git, отзовите его в Supabase и замените.

Если приложение сообщает, что таблица ещё не настроена, выполните SQL-скрипт и нажмите повтор синхронизации. Настройка проекта и реальная публикация не выполняются автоматически при создании файлов.

## Вход по email и личный доступ

1. В Supabase → Authentication → Sign In / Providers включите провайдер Email. Оставьте Confirm Email включённым, если используете регистрацию через приложение.
2. В Authentication → URL Configuration задайте Site URL: `https://esforgary.github.io/Calorie-calculator/`. В Redirect URLs добавьте этот адрес и локальный адрес `http://127.0.0.1:5173/`. Если Vite выбрал другой порт, добавьте точный адрес из терминала.
3. Создайте аккаунт через приложение, подтвердите email по письму и войдите. Альтернатива для личного дневника: создать пользователя с паролем в Supabase → Authentication → Users, затем войти в приложение.
4. После создания своего аккаунта отключите **Allow new users to sign up** в настройках Authentication. Email-провайдер оставьте включённым: он нужен для входа уже созданного пользователя. Если проект обслуживает другое приложение с открытой регистрацией, не меняйте этот общий переключатель без учёта второго приложения; для полной изоляции используйте отдельный проект.

Не следует считать скрытую кнопку регистрации защитой: ограничение новых аккаунтов устанавливается на стороне Supabase. [Официальные настройки Auth](https://supabase.com/docs/guides/auth/general-configuration).

В этой версии реализован вход по паролю и регистрация с подтверждением email. Отдельного экрана восстановления пароля пока нет; для личного проекта управлять аккаунтом можно через административный интерфейс Supabase.

## GitHub Pages

1. Загрузите проект в свой GitHub-репозиторий вместе с `package-lock.json`. `.env.local` не коммитьте.
2. Публичные URL и publishable key выбранного Supabase уже записаны в `.env.production`. Workflow использует их при сборке. Это клиентская конфигурация, а не административный секрет; приватность дневника обеспечивает SQL с RLS. Для другого проекта замените эти два значения.
3. В Settings → Pages выберите Source: **GitHub Actions**.
4. Отправьте изменения в `main` или `master` либо вручную запустите workflow **Deploy Kall to GitHub Pages**. Он выполняет установку по lockfile, тесты, сборку и загрузку `dist` в Pages.
5. Добавьте итоговый адрес Pages в разрешённые URL Supabase Auth, как описано выше. После изменения `.env.production` заново запустите сборку: они встраиваются при компиляции.

В Vite задан `base: './'`, поэтому ресурсы работают и в подпапке репозитория. Приложение не требует отдельного сервера Node.js для работы. [Документация GitHub Pages с Actions](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Данные и синхронизация

- Гостевой дневник хранится только в этом браузере. При первом входе он **не переносится автоматически** в аккаунт. У каждого аккаунта отдельный локальный кэш по ID пользователя; выход возвращает гостевой дневник.
- Облачные данные сначала загружаются. Автосохранение начинается только после успешной загрузки; пустой экран при входе не заменяет облачный дневник. Во время загрузки изменения заблокированы. После сетевого сбоя можно работать с ранее сохранённым персональным кэшем; первый вход без кэша требует соединения.
- Изменения сохраняются локально сразу и отправляются в облако с небольшой задержкой. Без сети они остаются в браузере; повторите синхронизацию после восстановления связи. Не очищайте данные браузера, пока изменения не попали в облако или экспорт.
- Сервер увеличивает `revision` при каждом сохранении. Запись выполняется только при совпадении ожидаемой версии. При одновременном редактировании на разных устройствах конфликт останавливает отправку: новая облачная версия не затирается.
- При конфликте сначала экспортируйте текущий дневник, затем выберите загрузку облачной версии. Перед заменой приложение дополнительно сохраняет одну резервную копию в localStorage под ключом `kall:diary:USER_ID:v1:conflict-backup`. Если место закончилось, замена отменяется. Автоматического объединения двух версий нет.
- Повреждённый локальный JSON сохраняется без изменений в ключе с суффиксом `:corrupt-backup:TIMESTAMP` перед заменой. Если браузер не может записать резервную копию, исходный ключ не перезаписывается.
- На общем компьютере локальные копии остаются в браузере после выхода. Используйте отдельный профиль браузера и удаляйте его данные только после успешной синхронизации. Это важно для личной информации о здоровье.

Для переноса гостевых записей: скачайте JSON в «Профиль и цели», войдите в аккаунт и выберите «Восстановить из JSON». Импорт заменяет текущий дневник после явного подтверждения и скачивания его резервной копии. Экспортируйте дневник регулярно. Локальное хранилище может быть очищено браузером; облачная синхронизация не является историей резервных копий. Для проверки RLS можно создать два временных аккаунта: данные каждого должны быть видны только после входа в него. Проверку облака следует делать на реально настроенном проекте — локальная сборка сама её не подтверждает.

## Фотографии и ограничения первой версии

Фото продукта уменьшается интерфейсом до 512 пикселей по длинной стороне, с ограничением результата 350 КБ. Изображение хранится в JSON как data URL. Это удобно для небольшого личного каталога; base64 увеличивает размер примерно на треть, а браузерное хранилище ограничено. Весь облачный дневник ограничен SQL-проверкой до 4 000 000 байт. Для большого каталога фотографий потребуется отдельный приватный Supabase Storage и ссылки вместо data URL.

Синхронизация передаёт весь дневник одной записью, история его версий не хранится. Рецепты и продукты вводятся вручную; шаги, прогулки и сон записываются пользователем, автоматического подключения к часам и шагомеру нет. Советы по времени активности показываются внутри приложения, фоновые push-напоминания не настроены.

## Расчёты

Калории продуктов, состав БЖУ, ИМТ, суточный ориентир, расход прогулок и сна являются оценками. Проверяйте значения продуктов на упаковке и указывайте вес съеденной порции. Калории сна и прогулок не следует повторно прибавлять к дневному бюджету, уже учитывающему обычную активность. Отдельный продукт сам по себе не гарантирует ускорения или замедления похудения: важны питание в целом, порции, сон, активность и особенности здоровья.

Расчёты предназначены для взрослого личного дневника и не заменяют медицинское назначение. При беременности, кормлении, возрасте вне диапазона 20–78 лет, заболеваниях или расстройствах пищевого поведения цели питания и нагрузки подбирают индивидуально со специалистом.
